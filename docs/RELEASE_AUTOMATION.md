# Release documentation automation

This automation keeps the public README, changelog, Release Notes, and repository description aligned with verifiable GitHub release state. It is independent from Android builds and does not read the `mfi-public-release` Environment.

## Sources of truth

- GitHub Releases API supplies published tag, draft/pre-release state, publication date, Release URL, and the actual uploaded asset names, links, sizes, and SHA-256 digests.
- The version ledger at `config/android-version-ledger.json` supplies application id, fixed signer identity, immutable `versionName`/`versionCode` allocations, and local artifact records. It does not establish that a version was published.
- `config/release-documentation.json` supplies the candidate summary, user-reported vehicle feedback, repository About description target, and managed marker identifiers.
- An APK is presented as verification-record checked only when its Release sidecar JSON agrees with the GitHub asset digest, package id, tag/version, fixed signing-certificate SHA-256, and required APK checks. The workflow reads the small JSON sidecar only; it does not download or execute APKs.

Internal APK metadata is never rewritten to match a display label. Historical tags and filenames remain exactly as GitHub reports them. Drafts are excluded; pre-releases are labeled separately; the latest formal Release is the newest published non-pre-release Release. Local candidates have no public download link.

## Managed document regions

The synchronizer edits only marker-delimited regions in the root `README.md` and `CHANGELOG.md`. It refuses to write when a marker is absent, duplicated, or out of order. All text outside those regions remains unchanged. Current Release Notes without a `CARPALY:RELEASE_NOTES` marker are left intact and reported as `UNMANAGED_PRESERVED`; new Release Notes created by the release publisher include a managed facts block.

Do not remove or copy managed marker pairs. To add hand-written context, place it before or after a managed region. Machine-generated release status must not be hand-edited inside the marker pair.

## Workflow behavior

- `android.yml` runs the Android checks on pull requests and pushes. Its `check` job also runs Python release/OTA tests, Bash publisher integration tests, workflow YAML/actionlint validation, immutable Action pin checks, Gitleaks, and the public-tree scan. No Release or MFi secret is exposed to that job.
- The `release_intent` job runs the full Android/test/archive checks for pull requests and branch pushes as well as main pushes; only the signer-only manual dispatch skips this job. It has read-only contents and pull-request permissions, and no Environment or secrets access. Its release decision publishes only for a `push` to `main` when `config/release-intent.json` changed in that exact main commit, is explicitly enabled, matches the current immutable version-ledger allocation and Gradle package version, and the main ref still points at the CI commit. Ordinary documentation/site changes, PR checks, tag pushes, disabled intents, stale commits, and failed CI skip publication. A beta intent creates a GitHub pre-release; a stable intent creates a formal Release.
- Before the APK signer runs, a read-only authorization job in the separate `release-policy-audit` Environment resolves the exact main commit's associated PR, verifies its same-repository source, non-draft/merged state, merge SHA, allowlisted human merger, active main ruleset, required CI context, and successful CI jobs. It also requires GitHub's rule-suite evaluation for that exact `refs/heads/main` commit to be `pass` and the named active ruleset's evaluation to pass; a `bypass` result or missing evaluation fails closed. It does not rely on the Rulesets API's `bypass_actors` field, which GitHub withholds from callers lacking ruleset write access; instead, it proves this merge did not use a bypass without asking for write permission. Direct pushes, ambiguous PR associations, unauthorized mergers, missing ruleset/evaluation evidence, and failed CI fail closed. `config/release-review-policy.json` explicitly selects the maintainer model. Its current `single_maintainer` mode matches the live zero-approval ruleset and requires the allowlisted owner to merge manually; it does not synthesize an approval or allow CI to merge/approve. GitHub records the merger identity but does not attest whether the owner clicked Merge in a browser or used another authorized client, so a browser-only action cannot be technically distinguished from available merge metadata. `multi_maintainer` mode requires at least one independent approval on the current PR head and a ruleset requiring at least that many approvals. Migration requires a reviewed main PR updating both the policy and GitHub ruleset consistently. The release-intent file must be changed in the resulting main commit; a stale commit or ordinary direct push is safely skipped/rejected.
- The authenticated Release job can run only on a `push` to protected `main` after successful full CI, the same-commit enabled release intent, and exact human-merge/ruleset authorization. Manual workflow dispatches and tag events cannot publish. It uses `mfi-public-release`, rebuilds from the reviewed main commit (never promotes a PR artifact), verifies the existing signer pin and MFi inputs, and creates the version tag together with a draft only after the APK, source ZIP, and checksums have passed local verification. It publishes only after remote asset re-download and digest checks. Existing conflicting tags/assets/releases are preserved and cause failure; published Release notes are never rewritten.
- Read-only Environment policy inspection reports that `mfi-public-release` allows both `main` and `v1.*.*`; no Environment settings were changed in Phase 10. The authorization job and automatic publisher still require the live Environment to permit the exact protected main ref before they can run.
- The publisher uses `GITHUB_TOKEN`. Release/tag events created with that token do not automatically start other workflows, so the post-publication job explicitly dispatches `pages.yml` and `release-docs-sync.yml` on `main`. `workflow_dispatch` is an allowed token-triggered exception. That job has only `actions: write` and `contents: read`; the Pages workflow and docs workflow retain their own permission/environment boundaries. It does not push a commit or create a recursive publication loop.
- `release-docs-check.yml` independently runs read-only metadata validation, workflow pin checks, and offline tests on relevant pull requests/pushes.
- `release-docs-sync.yml` runs on published/edited/deleted Release events, a daily reconciliation schedule, and manual dispatch. For Releases created by the authenticated publisher, it is explicitly dispatched after publication because `GITHUB_TOKEN` suppresses the Release event workflow. The follow-up waits for both Pages and documentation runs using a unique dispatch id, the expected `main` SHA, and each run's result; failures remain visible in the Android release run. It reads public release state and never builds an APK or reads signing/MFi secrets.
- The sync workflow updates a dedicated `automation/release-docs-sync` branch and opens or updates a Pull Request. It never commits directly to `main`, force-pushes, or auto-merges. If a merge conflict or GitHub permission failure occurs, it stops and preserves the existing branch/PR.
- Release Notes are patched only when the Release body already contains exactly one well-formed managed block. Identical text is not patched, preventing `release: edited` loops. Unmarked hand-written bodies are preserved.
- The authenticated publisher adds a managed facts block to newly created Release Notes. On rerun, already-published Releases are read-only; an existing draft's hand-written title and body are preserved, its channel must match the release intent, and only its draft flag is changed after every asset verifies.
- About synchronization changes only the repository description. Existing homepage and topics are read-only. If the description already matches, no admin token is needed. If it differs, the workflow needs the optional `CARPALY_REPO_ADMIN_TOKEN` repository secret with narrowly scoped repository-administration write access; otherwise the README/CHANGELOG sync succeeds and the About status is reported as blocked/proposed-only.
- The repository currently reports `can_approve_pull_request_reviews=false`. [GitHub's repository Actions settings documentation](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository) says this setting controls whether `GITHUB_TOKEN` may create or approve pull requests. The sync workflow does not approve PRs, but automated PR creation will require the repository owner to enable that setting or configure a narrowly scoped GitHub App/fine-grained token with contents and pull-request write access. Do not grant the signing or MFi secrets to the docs workflow.

The current repository description is intended to be:

> CarPaly — Android CarPlay receiver project with Geely Xingyue L (KX11) compatibility development.

The project homepage and topics are not rewritten by the description synchronizer.

## CarPaly Pages and signed OTA feeds

CarPaly now has its own original bilingual site generator in `scripts/build_site.py`. It reads only published GitHub Releases and matching APK verification sidecars through the existing `sync_release_docs.py` validation path. Drafts and unverified APKs receive no download link. The site is not an upstream APK mirror and never links to a DiPlay APK as a CarPaly installer. If a Release proof asset cannot be fetched, the build fails before deployment so the existing Pages deployment is left intact.

`.github/workflows/pages.yml` is the ordinary, secretless site path. It builds from published Releases and matching APK verification evidence into a fresh temporary directory, without entering a signing Environment or reading any Secret. The live `github-pages` Environment is currently restricted to `main`, so this workflow intentionally does not deploy from a Release/tag event; after authenticated publication, the publisher explicitly dispatches Pages on `main`. A manually created/edited Release must likewise be followed by a `workflow_dispatch` from `main`. A missing Pages home/state is not inferred to mean “never deployed”: the first static deployment is allowed only through `workflow_dispatch` on `main` with the explicit `allow_initial_static_bootstrap` confirmation, and only when both feed URLs also return canonical 404. On every successful deployment the site writes a per-channel `otaFeedEverPublished` marker. Subsequent builds require the home and marker to exist; a missing feed whose marker says it was previously published blocks deployment. Each present Stable/Beta feed must validate under the app-pinned trust store, be within its signed validity window, match a unique published, APK-verified historical Release of the same channel, tag, source commit, checksum URL/size, package version and signer, and have its public checksum sidecar re-verified; valid feed bytes are copied unchanged even if a newer verified Release is now shown on the site. A timeout, HTTP error other than 404, malformed/expired/untrusted signature, Release/source/checksum mismatch, missing previously published feed, missing history marker, or stale local feed blocks the whole deployment. The page builder displays “online updates unavailable” when there are no verified production feeds and never creates a placeholder feed.

`.github/workflows/publish-ota-feeds.yml` is the separate, manual production publisher. It only proceeds for an explicit dispatch from `main`; a no-secret preflight first requires the reviewed enabled `config/ota-publisher-policy.json`, an active app-pinned ECDSA P-256 trust key, and a real published Release whose APK proof, checksum, version ledger and tag ancestry all validate. Only then can the job enter `ota-manifest-publisher` and read its dedicated signing Secret. It signs and self-verifies the feeds against the exact preflight Release snapshot, then rebuilds the final site from that same snapshot and the locally signed feed files (including updated availability metadata and deployment-history markers). The deployment job alone receives `pages: write` and `id-token: write` in `github-pages`. Both Pages workflows share the same non-cancelling concurrency group, so whole-site deployments do not overlap. A preflight, signing, verification, or deployment failure leaves the previous published site/feed state intact.

The production publisher is deliberately not armed by this change: `config/ota-publisher-policy.json` has `productionEnabled=false`, `environmentConfigurationReviewed=false`, an empty key id, and the Android trust resource is empty. No OTA Secret, production key, or Environment was created or modified. A failed preflight occurs before the Environment-backed signing job. The workflow will not be usable until a production trust root is shipped through a reviewed app update and the dedicated GitHub Environment is manually protected and provisioned.

The feeds are `https://qwy20040320.github.io/carpaly/updates/stable.json` and `/updates/beta.json`. `scripts/build_ota_manifests.py` verifies published-release state, tag-to-main ancestry, APK verification records, actual checksum sidecar contents, package/version/signing proof, and the fixed Android signer before signing. Stable and Beta are separate; the app defaults to Stable and only checks Beta after an explicit selection. The client verifies an ECDSA P-256 signed payload against an app-bundled public-key trust store, then verifies the checksum sidecar, APK digest, package, version, and installed signer. It fails closed if the trust store is empty.

### OTA key setup and rotation (manual, not configured by this change)

1. A maintainer must create the production P-256 OTA signing key in an approved protected key-generation environment and retain a protected recovery copy. This repository must never generate or store a production private key, and no production key has been created in this task.
2. Add only the public X.509 DER key in Base64 and a reviewed key id/status to `common/src/main/res/raw/ota_manifest_public_keys.json` in a reviewed app update. The current trust resource is intentionally empty. Test keys are generated ephemerally by unit tests and are never shipped.
3. Install that signed CarPaly app through an existing trusted manual channel first; older installed versions without the OTA verifier/public key cannot securely bootstrap themselves through OTA.
4. Create and protect `ota-manifest-publisher` separately from `mfi-public-release`: allow only `main`, require at least one environment reviewer, and do not add MFi/APK-signing Secrets. After the app trust key and environment configuration have been independently reviewed, set `environmentConfigurationReviewed=true`, `productionEnabled=true`, and `keyId` in a reviewed main change; only then add `OTA_MANIFEST_SIGNING_PRIVATE_KEY_PEM` and `OTA_MANIFEST_SIGNING_KEY_ID` to that Environment. Do not reuse MFi, APK-signing, or repository-admin credentials.
5. Set **Settings → Pages → Build and deployment → Source** to **GitHub Actions** and use the independent `github-pages` deployment Environment. Neither the ordinary Pages builder nor the deployer receives the OTA private key; only the dedicated signer job binds it to the signing process.
6. For rotation, first ship the new public key in an app Release while the old key remains `retiring`; allow a bounded transition for active clients. Switch the Environment key id/private key only after that app Release is published. Mark compromised keys `revoked` in a reviewed app update and issue a new signed channel feed. Clients never fetch their own trust key from the feed.

If key provisioning, signed manifest generation, feed deployment, or download verification fails, the Pages artifact is not deployed. Production OTA publication can create signed unavailable tombstones for a channel with no eligible Release; ordinary site builds never create them. Feeds expire after 30 days and are rejected rather than silently accepted. Re-running the signer recomputes the highest verified eligible Release from current API state; shared workflow concurrency prevents overlapping whole-site deployments.

### Vehicle install safety

The app's current known vehicle API does not provide a validated parked/moving signal. The updater therefore never auto-opens Android's installer. If vehicle state is unknown, the user must explicitly attest that the vehicle is fully stopped, the parking brake is set, and CarPlay/calls/Siri/reversing-camera use has stopped; an active CarPlay session always blocks installer launch. This is a user assertion, not vehicle-state verification. A moving state blocks regardless of confirmation. Android still shows its package installer and asks the user to approve. Successful replacement install, retained settings, and post-update startup remain vehicle-test items.

## Manual GitHub configuration and signer verification

### Documentation sync permission

The current documentation workflow uses the built-in `GITHUB_TOKEN`, with only `contents: write` and `pull-requests: write` on its sync job, to push its dedicated branch and open/update a PR. To let that workflow create PRs, a repository owner must open **Settings → Actions → General → Workflow permissions** and enable **Allow GitHub Actions to create and approve pull requests**. The workflow itself never approves or merges a PR. If the repository owner does not want that repository-wide switch enabled, use a repository-scoped GitHub App or fine-grained token with only the contents and pull-request permissions needed for this one workflow; do not give it Release, Actions, MFi, or signing-secret access. The optional `CARPALY_REPO_ADMIN_TOKEN` is separate and is needed only if the repository description actually differs and is to be changed.

### Safe Release certificate check

Do not change `RELEASE_SIGNING_CERT_SHA256` to make an unknown keystore pass. The v1.1.4–v1.1.52 historical signer is `4d26d1c861b41a2cee4515e31f5f5c7eb13b9dd06e7485aa1687bc1d2ac73d90`; the explicitly authorized v1.1.53/code 41 signing epoch uses `d9b329525fc1ef21c365fab72c10367527cc038297c4f30eaa22b2207429139e` and cannot update those older packages in place. The cloud `mfi-public-release` Environment has not been migrated as part of local candidate work, so its current pin/keystore must not be assumed to match the new epoch.

1. In **Settings → Environments → `mfi-public-release`**, confirm only the names and scopes of these Environment Secrets: `MFI_IDENTITY_PK8_BASE64`, `MFI_CERTIFICATE_P7B_BASE64`, `RELEASE_KEYSTORE_BASE64`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS`, and `RELEASE_KEY_PASSWORD`. Confirm `RELEASE_SIGNING_CERT_SHA256` is an Environment Variable for the exact signer epoch being intentionally built. Do not change the current Environment to the new fingerprint unless the authorized new keystore has been transferred and verified through an approved protected process. GitHub intentionally does not reveal secret values; never echo them or place them in command arguments, logs, or source files.
2. On the trusted machine that holds the original Release keystore, inspect its public certificate using `keytool -list -v -keystore <protected-keystore-path> -storetype PKCS12 -alias <known-alias>`. Omit `-storepass` so keytool prompts interactively. Compare the reported SHA-256 certificate fingerprint, normalized to lowercase hex without colons, with the fixed value above and with `apksigner verify --print-certs <known-original-release-apk>`. Do not export the private key.
3. Compare the known alias with the value entered in the Environment without displaying the alias or password in logs. If a Secret must be repaired, set it only from the verified original keystore and credential source using an approved secure stdin-based process; do not guess passwords, substitute a new keystore, or change the pinned fingerprint.
4. The Android workflow has a separate `verify_release_signer_only` manual-dispatch mode. It is restricted to the `main` ref, receives only the four Release signer Secrets and the pinned fingerprint, has `contents: read`, reports the public certificate SHA-256 and a failure category, then deletes its temporary keystore. It does not receive MFi inputs, build an APK, create a tag, call the Release API, or upload assets. To use it, choose **Actions → Android checks → Run workflow**, select `main`, and set `verify_release_signer_only=true`. Authenticated APK Release has no manual/tag dispatch path.
5. Read-only Environment policy inspection reports that `mfi-public-release` allows both `main` and the existing `v1.*.*` release-tag pattern. No Environment policy was changed during Phase 10; recheck the policy in GitHub before any release.
